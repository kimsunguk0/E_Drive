# B arm(네트워크에 status 없음)의 축별 oracle (2026-09-10)

## 질문

status를 공통 특징 backbone에 아예 넣지 않고, 완성된 후보의 최종 선택에서만
주면 어떻게 되는가. 그 설계의 천장을 먼저 재야 한다.

## 방법

`temporal_b_history_s0_v1`(실제 과거 front −0.1/−0.5초, status는 어디에도
없음)에 C에 썼던 것과 같은 단계별 oracle 분해를 적용했다. 최종 유지 P20을
고정하고 속도 축만 넓힌다. 스크립트는 C 전용 가드(`common_status is True`)만
완화한 사본이며 계산은 동일하다.

## 결과

| 후보 집합 (P20 고정) | B oracle | C oracle |
|---|---:|---:|
| V10 (현재) | 0.884802 | 0.164612 |
| stage1 V64 | 0.606489 | 0.071460 |
| **전체 V1024** | **0.069498** | 0.067896 |

B의 base scorer D3는 1.587544, 실제 D3는 0.992639이다.
stage1 prune loss 0.536990, final prune loss 0.278313.

## 읽기

**B의 유지 경로는 C만큼 좋다.** 전체 속도를 붙였을 때 B가 0.069498,
C가 0.067896으로 차이가 0.0016뿐이다. status 없이도 영상이 경로를 제대로
고른다는 뜻이다.

**B가 못 하는 것은 속도 pruning 하나다.** V10에서 0.884802, V64에서도
0.606489다. 현재 속도를 모르면 어떤 속도 후보를 남길지 정하지 못한다.

따라서 "backbone에 status를 넣지 않고 최종 선택에서만 준다"는 설계의 천장은
**0.0695**이며 C(0.0679)와 사실상 같다. 다만 그러려면 네트워크가 속도를
쳐내게 두지 말고 **P20 × 전체 V1024 = 20,480개를 선택기가 직접 점수 매겨야**
한다. 32-d 특징은 순수 기하 + status + goal이라 후보별 영상 attention이
필요 없으므로 연산은 문제되지 않는다.

## 이 결과가 말하지 않는 것

천장이지 실현값이 아니다. C는 oracle 0.0715에서 실현 0.138이었다. B는
조건이 더 나쁘다.

- B의 base score가 훨씬 나쁘다(base_d3 1.587544). 32-d 특징의 마지막에
  들어가는 "centered base score"가 C에서만큼 유용하지 않다.
- 256-d 장면 토큰을 쓸 수 없다. 20,480개에 후보별 영상 attention을 돌리는
  비용 때문이다. 토큰은 충분히 학습했을 때 약 0.012 가치가 있었다.
- B 자체가 0.584에폭만 학습됐다. A 1.042 / B 1.000 / C 0.314라는 배치는
  "status가 필수"와 "status 없는 팔이 이 예산에서 학습을 못 했다"를
  구분하지 못한다.

parity 검사는 C의 기준 예측과 대조하도록 고정돼 있어 B에서는 실패로 표시된다
(candidate_id 756행 상이). 진단 수치 자체는 그 검사 전에 기록되며, B의 실제
D3 0.992639는 학습 시 기록된 B8 0.996320과 근사 일치한다.
